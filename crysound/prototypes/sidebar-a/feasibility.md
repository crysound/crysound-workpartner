# 侧栏方案 A：可行性说明

## 核实范围与结论

本说明依据前轮实际网页版及其已加载模块、本轮对主仓库侧栏、插槽、工作区、插件清单类型和品牌补丁的源码复核。原型初版基线为 `7b8533b3fc`；本轮在原草稿分支继续修改。已定顺序见需求 #127 最新评论（11-07）：新对话 → 作品 → 自动化 → 市场 → 插件入口 → 最近对话。所有实现建议均为后续开发方案，本次只改静态评审材料。

方案 A 可以实现，单靠品牌 CSS 不够：布局与颜色适合放品牌层，搜索命令、按工作区数量选择列表、更多会话展示、固定入口排序与插件入口折叠需要组件改动。优先利用既有插槽和服务；确需改变 dsh 组件的地方做小范围、可核对的包补丁或源码修改。不要通过搬运 React 管理的 DOM、伪造点击、长期依赖散列类名来替代组件逻辑。

## “我的工作台”是个人插件，不并入作品

前轮实际浏览器加载模块 `@local/my-workbench`，以 `my-workbench` 注册 `main` 页面和 `sidebar.panellist` 入口（`order: 25`），展示本人飞书待办、日程、项目统计与跟进。本轮伙伴助理及需求单评论已明确：这是负责人自己安装的个人插件，同事没有。

因此保留它独立的插件入口，不并入作品，也不放个人菜单；原型只用虚构待办、日程和项目卡片示例。作品页仅保留创作成果，去掉“工作概览”页签。未安装个人插件的人不会凭空多一个入口，也不额外预装。工作台桌面数据服务与后端不在本单范围，无需将其列为正式侧栏开发的前置条件。

“作品”前轮来自加载中的 `dsh-claude-artifacts`，用 `joinArtifactsPage` 协调所有者；当前公司对应包为 `@crysound/artifacts`（见 `crysound/config/plugins.json`）。正式版只重排其入口，不覆盖页面或修改作品数据。市场、自动化和作品在有对应注册入口时按公司固定顺序显示；缺失或停用时不能伪造坏入口，须提示可恢复的安装或启用路径。

## dsh 入口顺序由什么决定，公司如何控制

| 层次 | 已核实的源码行为 | 对正式实现的含义 |
| --- | --- | --- |
| 插槽注册 | [`ui-slots/src/index.ts`](../../../packages/client/ui-slots/src/index.ts) 的注册账本先按 `priority`、再按 `order` 升序，同值保持注册先后；`entriesOfSlot` 按入口 id 选择有效注册。 | 注册顺序只是相同排序值的后备规则。注册先后受加载和重启影响，不等于安装先后。 |
| 侧栏元数据 | [`ui-sidebar/src/client/index.ts`](../../../packages/client/ui-sidebar/src/client/index.ts) 的 `syncPanels` 读取 `sidebar.panellist` 的 id、label、`order ?? 0`，再按 `order` 升序。市场 `plugins` 注册为 0（`ui-plugin-manager`），自动化 `schedules` 为 10（`ui-schedule`）；个人工作台前轮加载模块为 25。 | 全局主排序键是 `order`，相同值保留输入账本顺序。仅凭注册先后不能得到已定顺序；插件的负 `order` 也能插到固定入口前。 |
| React 渲染 | [`SidebarRoot.tsx`](../../../packages/client/ui-sidebar/src/client/SidebarRoot.tsx) 的新对话单独渲染在面板列表之前；面板按排序结果过滤未固定项后 `map`；市场由 [`panel-pins.ts`](../../../packages/client/ui-sidebar/src/client/panel-pins.ts) 固定。 | DOM 顺序是状态的结果。CSS `order` 不能同步键盘与读屏顺序，也不能实现数量门槛；不要搬动 React 的 DOM。 |
| 现有“更多” | `PanelMoreMenu` 依赖 `sidebar.panellist.actions` 是否注册，并由手动固定状态决定展示。公司 [`patch-market-entry.mjs`](../../scripts/patch-market-entry.mjs) 已把原生创建插件入口迁到市场。 | 它不按插件数量自动折叠。新“更多”只放额外插件面板，不恢复市场 / 创建插件的重复入口。 |
| 安装先后 | [`PluginInventoryEntry`](../../../packages/host/plugin-inventory/src/types.ts) 当前公开 entryId、moduleName、enabled、运行状态等，不含安装时间或安装序号；侧栏元数据也不含入口所属插件或安装时间。 | 不能把 `order`、文件修改时间、当前 DOM 或运行时首次出现顺序冒充安装历史。 |

公司可以稳定控制，但需要在侧栏元数据到展示列表之间增加明确的公司排序策略。新对话维持原命令；从有效面板中用稳定 id 识别作品、自动化、市场，按已定顺序输出，再追加其他插件面板。对额外面板忽略其跨分区的 `order`，新插件无论声明什么 `order`，均落在市场之后、最近对话之前。0 个不显示空占位，1–2 个直接展示，3 个及以上把全部额外入口收进“更多”；展开后仍按安装先后，点击保留原 `selectPanel` 和活动状态。一个插件多个入口时先按其安装序号、再按该插件内的 `order` / 注册顺序排列。

安装顺序需由插件安装层提供可持久化且跨重启稳定的序号，以及面板所属插件映射。更新、暂时停用再启用不改变原序号，卸载后重装分配新序号。既有插件若没有历史记录，无法还原真实安装时间；正式开发要核对现有配置是否保有可靠顺序，只有可证实的记录才可回填。若需新增持久结构，应先经分诊评审结构和旧安装处理办法，再开发；本原型用固定的示例安装序列演示，不创建或迁移用户记录。

排序策略放共享侧栏组件或版本匹配的公司包补丁，两端使用同一实现，不要求修改所有第三方插件的注册值。正式版还需对目标发布包和已安装官方作品版本复核稳定 id；单改公司 CSS 或调换插件加载顺序不足以保证长期稳定。

## 每项怎么做

下表改动量为阅读源码后的估计，不是已完成的变更统计。文件数与行数互相重叠，主要用于区分纯样式与组件改造的成本；不含安装历史回填、上游升级冲突或打包发布。

主壳与工作区合计预计涉及约 9–13 个文件、400–750 行逻辑 / 样式及相应行为检查；安装顺序来源与必要的持久结构变更另计。无需合并作品和个人工作台插件。正式开发前以目标运行时和真实插件版本再拆任务、收窄估计。

## 发布与跨端注意

网页版 Dockerfile 安装固定发布版 `@deepseek-ai/dsh@0.2.2-rc.1`，不是把本仓库 `packages/` 直接编进镜像；只改上游 TSX 源码不会自动改变线上网页。品牌 JS / CSS 两端已经注入，但品牌层不能替代列表与页面逻辑。

后续可优先做一个有版本匹配检查的共享包修补脚本（类似现有市场补丁），在网页版运行时安装后和桌面打包运行时应用**同一份**补丁，并在实际安装副本上跑两次验证幂等。现有 profile 的 `plugin-patches.mjs` 不等于一定能命中全局安装的客户端包；需明确脚本输入目录、包版本、原文命中和修补后的行为。若压缩包补丁无法小而清楚地维持，则改源码并构建两端可消费的公司版组件包；不要静默放行未命中的修补。也可上游提交通用扩展点，等发布后再去掉临时补丁。

本次不选择或实施发布路径，不改工作流、不消耗构建分钟、不改网关或镜像。正式实现上线由伙伴助理另行安排，桌面需要新客户端发布，不能把“共用源码”写成“已验证在已安装的桌面版生效”。

## 正式开发应逐项验收

1. 单工作区（包括真实无归属会话）、多个工作区、自定义分组 / 子工作区、从多个变回一个，均找得到原会话，目录与归属不变。
2. 会话重命名、置顶、归档 / 还原、拖动、运行 / 等待 / 未读状态、内容搜索和搜索定位仍然有效；没有创建权限时不显示新建操作。
3. 固定入口按新对话 / 作品 / 自动化 / 市场排列，市场之后才有额外插件；作品不含工作概览，个人菜单不含工作台；未安装者无入口。
4. 额外入口 0 / 1 / 2 / 3 个、首次安装、热加载、更新、停用再启用、卸载重装和应用重启后，顺序与“更多”门槛正确；较小或相同 `order` 不抢占固定入口。展开能打开全部插件，保持原功能与活动状态。
5. 相同窗口与样例下重新计算完整可见行数；浅色、深色、手机、收起、键盘导航、系统缩放与长中文标题检查。
6. 实际网页版下载可达，实际 Electron 无下载入口，Mac / Windows 顶部窗口控制与搜索快捷键正常。以上为后续验收清单，本轮只验证静态原型。
